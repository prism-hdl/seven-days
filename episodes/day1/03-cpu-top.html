聚在一处
组装与抽象

前两集只做了一颗模块。可一具能动的东西从来不是"一颗做很多事的模块"——它是许多颗各做一件事的模块，被线连起来。这一集讲第三组语法，写法只有一个逻辑：遇到了什么麻烦，于是就有了什么。

零件不等于身体

第 1 集的加法器、第 2 集的进程调度单元——都是一颗模块。一颗模块能做一件事：加两个数，或管好一个进程的一生。但一具能动的东西不是"一颗做很多事的模块"，而是许多颗各做一件事的模块，被线连起来。

于是 Prism 有第三组语法，专门回答一个问题：零件怎么聚成身体。这一组里每个手段都不是凭空设计的——都是被一个具体的麻烦逼出来的：

connect
两个零件要接上——于是有了最直白的接线：端口对端口。
wire
中间算出来的值要有名字——于是有了具名网线：可观测、可复用。
expose
要看见零件里面的状态——于是把它引到顶层，不改叶子模块一根端口。

三种连接手段

connect · 两个端口要接上

零件拼到一起，第一件事就是接线。两个端口一对一、中间不需要任何加工——这就是最小的一种连接。左端必须是被驱动的（输出 / inout），右端是被注入的（输入 / inout）：

prismdesign 体内
design link {
    s : src
    k : sink
    connect s.q -> k.d
}

wire · 中间的值要有名字

可线并不总是一对一的直连：有时中间要先算一步；有时这根线要被多处引用，还要出现在观测表里。于是有了 wire——把一段表达式落到一根具名网线上，再推给下游端口。一行可以写全，也可以拆开写：

prism三种 wire 形态
// ① 一行全包：声明 + 驱动 + 推送
wire step : u8 = t.c + 1 -> d.x

// ② 只声明 + 驱动：值可被 show 观测，口子另接
wire res  : u8 = d.y

// ③ 只声明：驱动与推送都后置（大网表里把线集中在一处画）
wire cause : u8
cause = match { illegal => 2, ebreak => 3, _ => 0 }
cause -> ctrl.trap_cause

expose · 里面的状态要看得见

接完线还有一件麻烦事：看不见它。线全在里面跑，你想确认"里面的状态真的在跳"——总不能在叶子模块上凿一排调试端口。于是有了 expose：观测点不加在叶子身上，加在顶层：

prismdesign 体内
expose rf.regs[1] as x1     // mem 元素
expose pc.addr    as pc_obs // reg
为什么需要 expose？

一个寄存器堆为了能把 x1..x30 露出来做仿真观测，传统写法要把它撑成 32 端口模块（dbg_x1 … dbg_x30）；每加一个观测点就得改叶子模块 + 改它的 @schedule interface。有了 expose，regfile 保持干净，观测归顶层。

拼一条迷你数据通路

三个手段都到手，拼一具小的试试。三颗模块：一颗心跳（每拍 +1）、一颗倍法器（×2）、一颗比较器（≥16 报 1）。它们之间用两根 wire 连起来——心跳驱动、逐级加工、末级判断，形状上已经是一条完整的链路。

prismmini_cpu.prism · 模块部分
module ticker {
    in  en  : Signal<u1>
    out c   : Signal<u7>
    reg cnt : u7
    on clock { cnt' = en ? cnt + 1 : cnt }
    c = cnt
}

module doubler {
    in  x : Signal<u8>
    out y : Signal<u8>
    y = x + x
}

module thresh {
    in  x   : Signal<u8>
    out hit : Signal<u1>
    hit = (x >= 16) ? 1 : 0
}

design mini_cpu {
    t : ticker
    d : doubler
    h : thresh

    wire step : u8 = t.c + 1 -> d.x
    wire res  : u8 = d.y     -> h.x

    expose t.cnt as ticks
}

这份文件里站着两类声明：三颗 module 各说"我做什么"，一份 design 说"它们怎么拼"。design 是这个语言里唯一"看得见全局"的地方——一份拼装图里只有三样东西：实例（谁在场）、接线（谁接谁）、观测（看什么）。三条规矩值得展开：

  • 实例化写 名字 : 模块——同一颗模块可以例化多份，各起各的名字；名字唯一，名字.端口 就是引用它的方式（上面 t.c / d.y / h.x 都是）。
  • 顶层端口是推导出来的——没被任何 connect / wire 接走的输入端口，就是顶层输入；没被接走的输出，就是顶层输出。看上面那份：t.en 没人接 → 它就是要被驱动的顶层输入；h.hit 没人接 → 它就是要被观测的顶层输出。端口表不用手写——"谁还没被接走"自己说了算，下一节的跑表里就能看到这两个名字。
  • design 不写行为——没有 reg、没有 on clock：跨拍的状态住在零件（module）里；design 只做"接线上的加工"（wire 右值：取位、拼宽、常量）。唯一的例外：一台 fsm 要统管几颗实例时，它写在 design 里——那是后日流水线的事。

三颗模块各自还能单独跑——这是模块化的硬指标；拼装图只是把它们的端口连起来，零件内部一行行为都没改写。

跑起来：一条通路，三处观测

设计写完了，说话要算数——跑一遍。喂激励、盯观测、定停机：

prismmini_cpu.prism · run 段
run mini_cpu_check of mini_cpu {
    stim : {
        t.en, [ticks, step, res, h.hit] = {
            1, [ 1,  2,  4, 0],
            1, [ 2,  3,  6, 0],
            …（中间略）
            1, [ 7,  8, 16, 1],   // res 越过 16，hit 起效
            1, [10, 11, 22, 1],
        }
    }
    until : end of stim
    show  : { t.en, ticks, step, res, h.hit }
}

注意观测列里同时出现了三种东西：t.en 是没被占用的顶层输入、ticks 是 expose 出来的实例内部寄存器、step / res 是具名 wire。h.hit 则是没被连走的输出端口。

这三个手段的边界，动手碰一下最清楚：把 t.c + 1 改成 + 3——动的只是这条线及其下游期望，叶子模块一行不用碰；把 wire res : u8 = d.y -> h.x 拆成「只算不推的 wire + 单独的 connect d.y -> h.x」——两种写法都跑得通，但生成的 RTL 不同：h.x 的驱动源从 res 换成了 w__d__y，res 退化成一根只为观测存在的线（连线与观测是两件事）；再试着 expose 一个组合信号（d.y）——check 还过得去，gen-rtl 当场拒绝：'y' 不是 reg（origin=local）；mem 需写 'inst.y[i]'（expose 只服务 reg / mem 这类状态，不是万能探针）。

世界突然复杂了

三颗模块、两根线，手写得起。可真实的工程不是三颗——是几十颗模块、上百根线、好几个文件。世界突然复杂了，于是 Prism 还得再往上给一层——还是同一个逻辑：遇到了什么麻烦，于是就有了什么。

interface · 零件多了，得先立规矩

零件一多，第一个问题不是"怎么连"，而是"怎么保证每个零件都长对了"。三颗模块可以靠眼睛对端口，三十颗就不行了。于是有了 interface：把"一组端口"写成一份契约——名字、方向、位宽，逐项钉死：

prismbox.prism · 契约与它的实现
interface Accumulable {                  // 契约：一份"端口 + 方向"的清单
    in  din : Signal<i8>
    in  en  : Signal<u1>
    out q   : Signal<i8>
}

module acc implements Accumulable {      // 声称遵从——端口逐项对齐
    in  din : Signal<i8>
    in  en  : Signal<u1>
    out q   : Signal<i8>

    reg r : i8

    q = r

    on clock {
        if (en) {
            r' = din                     // 使能那拍：din 装进 r
        }
    }
}

模块一旦声称 implements，端口就必须与契约逐项对齐——写对了，typecheck 会回一条 实现接口: Accumulable ✓；对不上，编译当场停下、点名是哪个端口：

▸ prism typecheck · 两处"对不上"的写法
[err] [module acc_missing] 实现接口 'Accumulable' 缺少端口 'q' （interface 定义 line 4） [err] [module acc_wide] 实现接口 'Accumulable' 端口 'q' 位宽不匹配：期望 8，实际 16 （interface line 4, module line 18）

契约还有第二种用法：当插槽——"我要一颗实现了 Accumulable 的模块，至于是哪一颗，例化时再给"。这正是下一段的主角。

composer · 几颗零件装成一颗更大的零件

第二个麻烦：几颗零件总是绑在一起干活，你却每次都要把它们之间的线重画一遍。于是有了 composer：把这套"零件 + 它们之间的线"封成一颗更大的零件——外面只看得到一圈端口：

prismbox.prism · 封装与例化
composer Box<A: Accumulable> {           // 插槽式封装：A 必须是实现了契约的模块
    in  din : Signal<i8>
    in  en  : Signal<u1>
    out q   : Signal<i8>

    a : A                                // 插槽：例化时放进一颗具体模块

    connect din -> a.din                 // 盒内接线：外面进来 → 里边那颗
    connect en  -> a.en
    connect a.q -> q                     // 里边那颗 → 外面出去
}

design box_top {
    b : Box<A = acc>                     // 把上面那颗 acc 放进插槽
    expose b.a.r as r_obs                // 观测穿透：读盒里那颗 acc 的 r
}
  • 展平是纯编译期的事——composer 不花硬件：RTL 里没有"包装模块"这一层，它就是内部实例 + 那几根线本身。
  • 例化与 module 同套——b : Box<A = acc>：<> 里收的是定义（把 acc 放进插槽 A）。另一种实参 (...) 收的是实例本身——例化处写 (p = u_src)，指的是父层已经存在的那份实例；展平后直接指向它、不复制第二份（后日的流水线会用到）。
  • 盒子里能写什么——一圈端口 + 内部实例 + wire / connect / 表达式；reg / mem 这类时序状态不放 composer——时序状态住在被它封进来的 module 里。

跑一下——激励从盒外打进去，观测从盒子深处读出来：

prismbox.prism · run 段
run box_check of box_top {
    stim : {
        b.din, b.en, [b.q, r_obs] = {
             7,    1,    [7, 7],
             9,    1,    [9, 9],
             9,    0,    [9, 9],        // en 拉低：r 保持上一拍的值
        }
    }
    until : end of stim
    show  : { b.din, b.en, b.q, r_obs }
}
▸ prism run examples/box.prism --debug
cycle b__din b__en b__q r_obs 0 7 1 7 7 1 9 1 9 9 2 9 0 9 9 # expect: 3/3 拍有断言 · 2 列 · 全等 ✅

列头里 b.din 显示成了 b__din——composer 展平后实例名逐段相接（第 2 集讲过的 __ 分隔符）。而写法两边都不用改：外面照旧 b.din、里面照旧 a.din，expose 的路径也能继续往多层盒子里写。

import · 工程大了，得分开装

第三个麻烦在"装"这个字本身：一个文件塞不下几十颗零件。于是有了 import：把工程拆到多个 .prism 文件——每颗（或每组）零件一个文件，顶层一份 import 清单。文件边界就是检视边界：想知道一个子系统长什么样，去看它那个文件。

小结 · 第一日的三件兵器到齐

把三日连起来看：

  • 第 1 集给了动机——两层黑暗，Prism 用一份源码三下降回应。
  • 第 2 集给了一颗模块的写法——分层、类型、组合与时序、状态机。
  • 第 3 集给了多颗模块的写法——design 把零件聚成身体（connect / wire / expose）；零件多了，有 interface 立契约、composer 封子系统、import 分文件。
