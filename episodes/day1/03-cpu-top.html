聚在一处
从模块到 CPU

前两集只做了一颗模块。但 CPU 从来不是一颗模块——它是六颗模块加几十根线。这一集讲第三组语法：怎么把散落的零件聚成一体，以及当零件多到六个时，为什么必须再往上抽象一层。

零件不等于身体

第 1 集的加法器、第 2 集的饱和计数器——都是一颗模块。一颗模块能做一件事：加两个数、数到饱和。但一台计算机不是"一颗做很多事的模块"，而是许多颗各做一件事的模块，被线连起来。

Prism 在这里有第三组语法，专门回答一个问题：零件怎么聚成身体。

connect
端口对端口，直连。最直白的一种接线。
wire
把一段表达式落到具名网线上，再推给下游端口。名字可以观测、可以复用。
expose
把实例内部的 reg / mem 引到顶层做观测端口——不改叶子模块一根端口。

三种连接手段

connect · 端口对端口

最朴素的一种。左端必须是被驱动的（输出 / inout），右端是被注入的（输入 / inout）：

prismdesign 体内
design cpu {
    s : src
    k : sink
    connect s.q -> k.d
}

wire · 表达式落到具名网线

当两端之间不只是"直连"、还想给这根线起个名字时用它。一行可以写全，也可以拆开写：

prism三种 wire 形态
// ① 一行全包：声明 + 驱动 + 推送
wire step : u8 = t.c + 1 -> d.x

// ② 只声明 + 驱动：值可被 show 观测，口子另接
wire res  : u8 = d.y

// ③ 只声明：驱动与推送都后置（大网表里把线集中在一处画）
wire cause : u8
cause = match { illegal => 2, ebreak => 3, _ => 0 }
cause -> ctrl.trap_cause

expose · 把内部状态引出来

叶子模块保持"干净的 7 个端口"，观测点不加在它身上——加在顶层：

prismdesign 体内
expose rf.regs[1] as x1     // mem 元素
expose pc.addr    as pc_obs // reg
为什么需要 expose？

一个寄存器堆为了能把 x1..x30 露出来做仿真观测，传统写法要把它撑成 32 端口模块（dbg_x1 … dbg_x30）；每加一个观测点就得改叶子模块 + 改它的 @schedule interface。有了 expose，regfile 保持干净，观测归顶层。

拼一条迷你数据通路

三颗模块：一颗心跳（每拍 +1）、一颗倍法器（×2）、一颗比较器（≥16 报 1）。它们之间用两根 wire 连起来——形状已经很像 CPU 的取指→执行→判分支。

prismmini_cpu.prism · 模块部分
module ticker {
    in  en  : Signal<u1>
    out c   : Signal<u7>
    reg cnt : u7
    on clock { cnt' = en ? cnt + 1 : cnt }
    c = cnt
}

module doubler {
    in  x : Signal<u8>
    out y : Signal<u8>
    y = x + x
}

module thresh {
    in  x   : Signal<u8>
    out hit : Signal<u1>
    hit = (x >= 16) ? 1 : 0
}

design mini_cpu {
    t : ticker
    d : doubler
    h : thresh

    wire step : u8 = t.c + 1 -> d.x
    wire res  : u8 = d.y     -> h.x

    expose t.cnt as ticks
}

三颗模块各自还能单独跑——这是模块化的硬指标。design 层只写"谁接谁"，不写任何计算。

跑起来：一条通路，三处观测

prismmini_cpu.prism · run 段
run mini_cpu_check of mini_cpu {
    stim : {
        t.en, [ticks, step, res, h.hit] = {
            1, [ 1,  2,  4, 0],
            1, [ 2,  3,  6, 0],
            …（中间略）
            1, [ 7,  8, 16, 1],   // res 越过 16，hit 起效
            1, [10, 11, 22, 1],
        }
    }
    until : end of stim
    show  : { t.en, ticks, step, res, h.hit }
}

编译器给的是什么

prism gen-rtl 把上面那份 design 下降成顶层网表。以下是我机器上的真实产物（节选）：

systemverilogmini_cpu.sv · 顶层网表
module mini_cpu_top (
  input  logic clk, rst_n,
  input  logic [1-1:0] t_en,
  output logic [1-1:0] h_hit,
  output logic [7-1:0] ticks
);

  // design-level wire 声明
  logic  [7:0] step;
  logic  [7:0] res;

  // 内部连线（connect 生成）
  logic  [7-1:0] w_t_c;
  logic  [8-1:0] w_d_y;

  // expose 观测线（子模块输出端口引出，非层次引用）
  logic [7-1:0] w_xpose_t_cnt;

  // 子模块例化（clk/rst_n 分发）
  ticker_rtl t (.clk(clk), .rst_n(rst_n), .en(t_en), .c(w_t_c), .xpose_cnt(w_xpose_t_cnt));
  doubler_rtl d (.clk(clk), .rst_n(rst_n), .x(step), .y(w_d_y));
  thresh_rtl h (.clk(clk), .rst_n(rst_n), .x(res), .hit(h_hit));

  // design-level 组合 assign
  assign step = (w_t_c + 1);
  assign res  = w_d_y;

  // 观测 assign（expose，走子模块输出端口）
  assign ticks = w_xpose_t_cnt;
endmodule

三件值得注意的事：

  • clk / rst_n 自动分发——三颗子模块各接一根，不用你写第三遍。
  • 被 connect 占用的端口会生成中间线（w_t_c / w_d_y），顶层模块的端口表因此只留没被连走的那些（t_en / h_hit）。
  • expose 不下跨层次引用——它给子模块加一个 xpose_cnt 输出端口，再在顶层 assign 出来。为什么绕这一下？因为 yosys 不解析 SV 的跨层次路径引用，直接写 t.cnt 会静默产出无驱动的网表。

当零件变成六个

三颗模块手连两根线，很轻松。真实的 CPU 是什么规模？这是白虹（Whitebow）单周期 CPU 的顶层——一颗能跑 RV32I / RV64I 双模的真核：

prismwhitebow_sc.prism · design 段（节选）
design whitebow_sc {
    // ==== 实例化子系统（Composer）====
    ctrl : ControlPath<T=i64, Dec=decoder, CSR=csr, Imm=immgen>
    exec : ExecutionPath<T=i64, ALU=alu, MD=muldiv>

    // ==== 独立模块 ====
    pc   : pc<T=i64>
    im   : sram              // 指令存储器（可替换为 ROM/DDR）
    dm   : sram              // 数据存储器（可替换为 DDR）
    rf   : regfile<T=i64>

    // ============ design-level wire 声明 ============
    wire mode32  : u1 = ctrl.mode32 -> exec.mode32
    wire iaddr   : u8 = pc.addr[9:2] -> im.addr
    wire rf_wen_eff : u1 = ctrl.rf_wen & legal -> rf.wen
    …  全文共 45 根 wire / 2 个 Composer / 1 条 import 链
}

六颗实例（2 个 Composer + 4 个独立模块）、45 根具名 wire。规模一上来，"平铺"就不够了——于是有了上层的抽象手段：

手段解决什么
Interface契约：一组端口的集合，写成类型。模块实现某个 interface，就保证端口集合齐全——可替换、可复用。interface Decodable { in instr : Signal<u32> … }
Composer封装：把紧耦合的几颗模块封成一个子系统，内部连线收在 composer 体里；顶层只看见一组端口，不必重复画那批线。ControlPath 就封装了 decoder + csr + immgen，替顶层省掉 ~15 条手动连线。
import切分：把工程拆到多个 .prism 文件。白虹用 1 条 import "iu/interfaces.prism" 起头，串起 8 个部件。
blackbox逃逸：外部 SystemVerilog IP 作为原语例化进来——Prism 只按端口清单生成例化连线，不生成模块体。复合总线协议（AXI / DDR 控制器）由此绕过 Prism 语法，而不是硬塞进语言。
prismblackbox 例化外部 IP
blackbox ext_core {
    verilog  : "vendor/extcore/extcore.sv"
    filelist : "vendor/extcore/extcore_rtl.fl"
    in  clk        : Signal<i1>
    out retire0    : Signal<i1>
    out retire0_pc : Signal<i40>
}

design tb_top {
    core : ext_core
    sink : trace_sink
    connect core.retire0    -> sink.retire_in
    connect core.retire0_pc -> sink.retire_pc_in
}
blackbox 的边界是诚实的

blackbox 只在 RTL 后端可用：TLM 后端编译期报错（外部 SV 没有 SystemC 语义），golden 后端也报错（没有 Python 求值语义、不可参与 cosim）。拒绝静默降级——不会给你一个"少了这块"的模型让你过。

小结 · 第一日的三件兵器到齐

把三日连起来看：

  • 第 1 集给了动机——两层黑暗，Prism 用一份源码三下降回应。
  • 第 2 集给了一颗模块的写法——分层、类型、组合与时序、状态机。
  • 第 3 集给了多颗模块的写法——connect / wire / expose 把零件聚成身体，Interface / Composer / import / blackbox 让规模可控。
"神称旱地为地，称水的聚处为海。神看着是好的。" —— 《创世记》 1:10

下一集是第一天最后一集——让光打出去。不写新代码，只把这些东西的真实产物摆出来：gen-rtl 出的 SV、送上 FPGA 的 bitfile、串口打出来的 OpenSBI banner。看完你会知道：这门语言真的能造芯片。

练习

  1. 把 wire step : u8 = t.c + 1 里的 + 1 改成 + 3——stim 表的期望要怎么改？改完三次下降是否仍全绿？（这一题想让你体会：改一条 wire 就是改一条数据通路，不用碰任何叶子模块。）
  2. 把 expose t.cnt as ticks 改成 expose d.y as ...——试试 expose 一个组合信号会报什么错（实测：'y' 不是 reg（origin=local）；mem 需写 'inst.y[i]'）。这能帮你记住：expose 只服务 reg / mem 这类状态，不是万能探针。
  3. 删掉 wire res 行的 -> h.x，改成一条单独的 connect d.y -> h.x——两种写法都跑得通，但生成的 RTL 不同：h.x 的驱动源从 res 变成了 w_d_y，而 res 退化成一根只为观测存在的线。"连线"与"观测"是两件事，可以分开。
