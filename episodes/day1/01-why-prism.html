一道裂缝
为什么要有 Prism

混沌不是没有工具——恰恰相反，硬件世界有两层黑暗：同一个硬件被写了两遍（RTL + TLM，等价性靠人盯），而语言本身没有软件开发的精神与思想（没有类型、没有泛型、没有模式匹配）。Prism 同时回应这两层——一份源码三下降解决结构，类型驱动解决表达。

混沌：两条割裂的路

硬件开发有两条路。它们描述同一个电路，却要各写一遍——

RTL 路径
Verilog / SystemVerilog / VHDL。周期精确、可综合、可流片。代价：算法与微架构缠在一起——一份 FIR 想改流水级，得动 40 处 wire / reg / mux；always @(posedge clk) 里 = 与 <= 一位之差就能出幽灵锁。
系统建模路径
SystemC / TLM。事务级、快数个数量级，适合架构探索与作为黄金参考。代价：不可综合——它与最终 RTL 之间的一致性全靠人工维护，两边演进不同步是常态。

两条路各写一遍意味着：同一颗硬件的行为等价性无保证。你写完 RTL、写完 TLM，跑仿真看两边算出的数是不是相同；改一个字段，两边都要动；漏动一遍，仿真器与综合器各自解释——这就是"黑暗"。

HLS 部分弥合了"算法 → RTL"——但它吃的 SystemC 输入是可综合子集，产不出用于架构探索的 TLM 快模型；反过来，手写 TLM 也无法综合。HLS 只补了半半。

但还有一层更深的黑暗——一个写了十年 Rust / TypeScript / Python 的软件工程师第一次打开 Verilog 文件时，他不会说"这语言有两条路"，他会说："这语言不想我说话。"

  • 没有类型——只有 wire 和 reg，位宽靠 [31:0] 数数，符号靠人脑记；
  • 没有泛型——想把 8 位加法器加宽到 32 位？复制粘贴、全局替换；
  • 没有模式匹配——所有分支都是 case + default + 手写位段宏；
  • 没有表达式——你想写 sum = a + b，它要你声明 wire [31:0] sum; + assign sum = a + b;，再告诉综合器这不是 latch；
  • 没有包管理、没有类型检查器、没有 LSP、没有 --help 能直接跑通的 30 秒上手。

软件世界的语言在进化——从 C 到 Rust、从 Java 到 Kotlin——每一代都在让编译器替人多想一步。硬件描述语言停在 1985。不是它"不够快"，是它不配当一个工程师用来思考的工具。

问题的核心——两层黑暗

结构层：同一个硬件被写了两遍（RTL + TLM），两遍的等价性没有编译器的保证。

表达层：语言本身没有软件开发的精神与思想——没有类型、没有泛型、没有模式匹配、没有"让编译器替人想"的哲学。对软件工程师来说，Verilog 不香——不是它做不了事，是它不让你用思考的方式做事。

Prism 同时回应这两层：一份源码三下降解决结构；类型驱动 + 泛型 + match + Interface 解决表达。

神说：要有光

Prism 的答案：一份源码，同时下降为可综合 RTL 与 SystemC/TLM 模型——再加一路独立 Python 黄金参考——三条通路一起走，逐拍对撞。

编译器从同一棵 AST 分头下降到三个后端：

RTL · SystemVerilog
可综合 · 周期精确
TLM · SystemC
事务级 · 架构探索快模型
Golden · Python
解释 AST · 独立 oracle

三份产物喂同一份激励，逐拍 / 逐事务比对，差异即报错——行为等价性由编译器保证，不再靠人盯。

最小的一束光：一颗加法器

第一集不谈深——只把这份"同源三下降"落到最小可行示例。三个端口、一句 sum = a + b、一段 run 激励；20 分钟从源码走到三份产物、再三路全绿。

prism adder.prism 
module adder {
    in  a   : Signal<u32>
    in  b   : Signal<u32>
    out sum : Signal<u32>

    sum = a + b
}

@schedule adder {
    bitwidth  : { data:32 }
    pipeline  : 1 stage
    reset     : async_low
    clock     : 100 MHz, domain = single
    resource  : none
    latency   : 1 cycle
}

design adder_top {
    dut : adder
}

run adder_check of adder_top {
    stim : {
        a, b, [sum] = {
                  1,          2,            [3],
                 10,         20,           [30],
                100,        200,          [300],
        }
    }
    until : end of stim
    show  : { a, b, sum }
}

这一份源码里已经有 Prism 的四件关键事——但先不展开。

  • 算法层（module adder）——只写"做什么"：sum = a + b——整个模块的行为就这一句；端口用 in / out 显式标方向（不靠"有没有被赋值"倒推）。
  • 调度层（@schedule adder）——只谈"怎么做"：位宽、流水、时钟、复位。存储、接口这类能从模块体推断的字段，整条可以省略——语言自己推。它把微架构从算法里剥出来，独立成一个语法块。
  • 类型驱动（Signal<u32>）——32 位无符号；+ 自动扩一位防进位、按目标类型截回，截断永远显式。位宽是编译期推出来的账、回绕是 32 位的物理事实——都不用拿脑子记。
  • 仿真入口（run adder_check）——表式 stim 一次声明列头，每行末尾 [...] 是手算期望；跑一次就是一次自判定。3 拍 × 3 行全对，编译器打"expect: 3/3 全等 ✅"。

信息不足时，编译器不猜：把 bitwidth : { data:32 } 删掉——golden 还能跑，而 gen-rtl 会直接拒绝：无法下降为 RTL（缺调度信息）… missing=['bitwidth']。拒绝下降，不静默产出劣质电路。

第 2 集再讲这四件；这一集只看一件事——三条通路第一次同拍发出同一个数值。

三道棱面 · 逐拍同数

三条命令、三次下降、三份产物。每一条都在同一颗 CPU（编译器）上、同一份激励上、跑同样的 3 拍：

① Python golden 直跑

bash shell 
prism run examples/adder.prism --debug
▸ golden · Python 解释 AST
# run: adder_check design: adder_top stop: end of stim (3 cycles) cycle a b sum 0 1 2 3 1 10 20 30 2 100 200 300 # expect: 3/3 拍有断言 · 1 列 · 全等 ✅

这一份是 golden——Python 直接解释 AST 得到的逐拍表；独立、快、可读。表尾 # expect: 3/3 ... 全等 ✅ 说的是每一行的手算期望 [3] [30] [300] 都命中——golden 一侧自己就能判定跑对没有。

② RTL 通路 · iverilog 真仿真

bash shell 
prism run examples/adder.prism --rtl --debug
▸ RTL · SystemVerilog + iverilog
[run] adder_check: RTL tb 跑完，3 拍（产物 …） # run: adder_check design: adder_top cycle a b sum 0 1 2 3 1 10 20 30 2 100 200 300 # stop: end of stim (3 cycles) [run] adder_check: RTL 期望值比对 # expect: 3/3 拍有断言 · 1 列 · 全等 ✅

--rtl 换到第二条腿：编译器把同一份 .prism 下降成 SystemVerilog，iverilog 真跑——输出的表和 golden 那张逐格相同，同一份手算期望也在 SV 侧过一遍，这就是表尾那行 RTL 期望值比对。RTL 后端的下降 bug（位宽截断错、符号性错、握手错）逃不过这份期望。

③ TLM 通路 · SystemC 事务级

bash shell 
prism run examples/adder.prism --sim systemc --debug
▸ TLM · SystemC + g++
Info: /OSCI/SystemC: Simulation stopped by user. [run] adder_check: 3 拍 SystemC 模型直跑完成 cycle a b sum 0 1 2 3 1 10 20 30 2 100 200 300 [run] adder_check: TLM 期望值比对 # expect: 3/3 拍有断言 · 1 列 · 全等 ✅

--sim systemc 换到第三条腿：编译器把同一份 .prism 下降成 SystemC/TLM C++ 源码，g++ 编译、跑 SystemC 内核，忽略调度层塌缩为事务跳转——输出的表和 golden 那张逐格相同，同一份手算期望在 TLM 侧也过一遍。TLM 的"时序抽象契约违反"，同样逃不过这份期望。

三次下降的合奏

通路 产物 仿真器 行级期望全等
GoldenPython AST直接解释✅ 3×3 全等
RTLSystemVerilogiverilog✅ 3×3 全等
TLMSystemC C++g++ + SystemC✅ 3×3 全等

三条通路全绿——同一份源码、三种编译产物、三张表逐格相同。判对错的不是人眼，是写进源码的同一份手算期望——谁写错了，谁的表就不会全绿。

三条路，互为反证
  • RTL 与 golden 是两套独立实现：一条走 Python AST 解释，一条走 SV 生成——任一条写错，它那张表就过不了同一份手算期望。
  • TLM 与 golden 也一样：TLM 忽略调度层、塌缩为事务，如果塌缩逻辑错、事务粒度错，期望那一关就会喊。
  • 三条都全绿，才轮得到"三份产物行为等价"这句话落地——不是人盯两遍代码，是同一份期望被三个后端各自命中。

再反过来试一次：把 sum = a + b 改成 a - b——三条腿照样跑、表照样出，但每一张表的行级期望当场喊 cycle 0 sum: 期望 3，实得 4294967295（无符号回绕是 32 位的物理事实：1 − 2 就是 2³² − 1）。不给一个"从不失败"的测试留活路——这就是行级期望的意义。

棱镜在手：安装与命令行

前面那三份产物，不是别处跑出来的——就在一台普通 Mac 上。装好工具、认清命令，这一节把地基铺平；后面每一集的命令，都从这里长出去。

bash install 
pip install prism-hdl          # 编译器本体（Python 3 包）
prism deps --install           # 按操作系统补齐仿真依赖（iverilog / SystemC 等）

git clone https://github.com/prism-hdl/seven-days
cd seven-days

只有 golden 直跑（prism run 的默认通路）全靠编译器本体，其它要的东西一次说清：RTL 那条腿（--rtl）要 iverilog，--sim systemc 那条腿还要 SystemC 与 C++ 编译器——这些归 prism deps 管：带 --install 就按操作系统把缺的补齐（只有 C++ 编译器不代装、提示你自己装）。装完看一眼自检报告，缺了哪件，它指名道姓：

▸ prism deps · 装完自检
[deps] 工具链自检：macOS（Homebrew） [ok] iverilog：Icarus Verilog version 13.0 (stable) (v13_0)（/opt/homebrew/bin/iverilog） [ok] C++ 编译器：/usr/bin/clang++ [ok] verilator：Verilator 5.052 2026-09-05 rev vUNKNOWN-built20260905 [ok] SystemC：/opt/homebrew/include/systemc.h [ok] sail_riscv_sim：0.14.1 全部就绪。golden 直跑（prism run）本就不需要外部工具；RTL 与 TLM 两条通路可用。

然后是记命令——不贪多，一张小地图就够走路：

bash 命令地图 
prism run        跑单一模型：默认 golden，--rtl / --sim systemc 换腿
prism gen-rtl    出可综合 SystemVerilog
prism gen-tlm    出 SystemC 模型源码
prism check      轻量检查（解析 + 可下降性）
prism typecheck  类型、位宽、可下降级别
prism dump-ast   编译器眼里的那棵树
prism deps       工具链自检：缺什么、怎么装
prism keywords   保留字登记表

两条参数规则先记牢：--debug 把观测一次开全——它等于 --show（出逐拍表）加 --util（判行内期望），想只要一样就单给那一个；--rtl 与 --sim systemc 负责换腿（默认 golden）。--run 名字 可以省——不给就跑遍文件里所有 run 块，一个文件有多段 run 时才需要点名。拿不准就裸跑 prism：全部命令与用法，它当面打给你看。

本集跑的 ①②③ 三条命令，就是 run 这条命令的最小用法；完整的九件工具，第四集一次走完。

神看光是好的

这就是第一集要讲完的唯一一件事——Prism 存在的理由：把两遍写、两遍盯、两遍改，合成一遍。

一颗 32 位加法器 sum = a + b——同一行代码，20 分钟前只是一段字符，现在它同时是：

  • 一段可综合 SystemVerilog，可以送进 yosys / Vivado 出 bitfile；
  • 一段 SystemC C++，可以挂进 gem5 / 事务级模型做架构探索；
  • 一张 Python 参考表，可以逐拍钉住前两条的输出。

三份产物行为等价——由编译器钉住，不再由人盯。

"神看光是好的，就把光暗分开了。神称光为昼，称暗为夜。有晚上，有早晨，这是头一日。" —— 《创世记》 1:4–5

光有了。从下一集起，我们把这份光掰开——第二集讲 Prism 的分层与语法骨架：`module` 与 `@schedule` 为什么必须分开，类型系统怎么把位宽和符号钉死，`reg` 与 `on clock` 与 `mem` 与 `fsm` 各自扮演什么角色。

第一日之后不再讲语法——因为光已经分开了。
