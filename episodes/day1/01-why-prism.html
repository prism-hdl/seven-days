一道裂缝
为什么要有 Prism

混沌不是没有工具——恰恰相反，硬件世界有两层黑暗：同一个硬件被写了两遍（RTL + TLM，等价性靠人盯），而语言本身没有软件开发的精神与思想（没有类型、没有泛型、没有模式匹配）。Prism 同时回应这两层——一份源码三下降解决结构，类型驱动解决表达。

混沌：两条割裂的路

硬件开发有两条路。它们描述同一个电路，却要各写一遍——

RTL 路径
Verilog / SystemVerilog / VHDL。周期精确、可综合、可流片。代价：算法与微架构缠在一起——一份 FIR 想改流水级，得动 40 处 wire / reg / mux；always @(posedge clk) 里 = 与 <= 一位之差就能出幽灵锁。
系统建模路径
SystemC / TLM。事务级、快数个数量级，适合架构探索与作为黄金参考。代价：不可综合——它与最终 RTL 之间的一致性全靠人工维护，两边演进不同步是常态。

两条路各写一遍意味着：同一颗硬件的行为等价性无保证。你写完 RTL、写完 TLM，跑仿真看两边算出的数是不是相同；改一个字段，两边都要动；漏动一遍，仿真器与综合器各自解释——这就是"黑暗"。

HLS 部分弥合了"算法 → RTL"——但它吃的 SystemC 输入是可综合子集，产不出用于架构探索的 TLM 快模型；反过来，手写 TLM 也无法综合。HLS 只补了半半。

但还有一层更深的黑暗——一个写了十年 Rust / TypeScript / Python 的软件工程师第一次打开 Verilog 文件时，他不会说"这语言有两条路"，他会说："这语言不想我说话。"

  • 没有类型——只有 wire 和 reg，位宽靠 [31:0] 数数，符号靠人脑记；
  • 没有泛型——改一个 8 位加法器成 32 位，复制粘贴、全局替换；
  • 没有模式匹配——所有分支都是 case + default + 手写位段宏；
  • 没有表达式——你想写 sum = a + b，它要你声明 wire [31:0] sum; + assign sum = a + b;，再告诉综合器这不是 latch；
  • 没有包管理、没有类型检查器、没有 LSP、没有 --help 能直接跑通的 30 秒上手。

软件世界的语言在进化——从 C 到 Rust、从 Java 到 Kotlin——每一代都在让编译器替人多想一步。硬件描述语言停在 1985。不是它"不够快"，是它不配当一个工程师用来思考的工具。

问题的核心——两层黑暗

结构层：同一个硬件被写了两遍（RTL + TLM），两遍的等价性没有编译器的保证。

表达层：语言本身没有软件开发的精神与思想——没有类型、没有泛型、没有模式匹配、没有"让编译器替人想"的哲学。对软件工程师来说，Verilog 不香——不是它做不了事，是它不让你用思考的方式做事。

Prism 同时回应这两层：一份源码三下降解决结构；类型驱动 + 泛型 + match + Interface 解决表达。

神说：要有光

Prism 的答案：一份源码，同时下降为可综合 RTL 与 SystemC/TLM 模型——再加一路独立 Python 黄金参考——三条通路一起走，逐拍对撞。

编译器从同一棵 AST 分头下降到三个后端：

RTL
SystemVerilog · 可综合 · 周期精确
TLM
SystemC · 事务级 · 架构探索快模型
Golden
Python 解释 AST · 独立 oracle

三份产物喂同一份激励，逐拍 / 逐事务比对，差异即报错——行为等价性由编译器保证，不再靠人盯。

最小的一束光：32 位加法器

第一集不谈深——只把这份"同源三下降"落到最小可行示例。三个端口、一句 sum = a + b、一段 run 激励；20 分钟从源码走到三份产物、再全绿对撞。

prism adder.prism 
module adder {
    in  a   : Signal<u32>
    in  b   : Signal<u32>
    out sum : Signal<u32>

    sum = a + b
}

@schedule adder {
    bitwidth  : { data:32 }
    pipeline  : 1 stage
    storage   : none
    interface : a, b, sum = Signal
    reset     : async_low
    clock     : 100 MHz, domain = single
    resource  : none
    latency   : 1 cycle
}

design adder_top {
    dut : adder
}

run adder_check of adder_top {
    stim : {
        a, b, [sum] = {
                  1,          2,            [3],
                 10,         20,           [30],
                100,        200,          [300],
        }
    }
    until : end of stim
    show  : { a, b, sum }
}

这一份源码里已经有 Prism 的四件关键事——但先不展开。

  • 算法层（module adder）——只写"做什么"：sum = a + b，一句数据流函数；端口用 in / out 显式标方向（不靠"有没有被赋值"倒推）。
  • 调度层（@schedule adder）——只谈"怎么做"：位宽、流水、存储、时钟、复位。它把微架构从算法里剥出来，独立成一个语法块。
  • 类型驱动（Signal<u32>）——32 位无符号；+ 会自动扩一位防进位、sum 的 u32 目标再截回来。截断永远显式。
  • 仿真入口（run adder_check）——表式 stim 一次声明列头，每行末尾 [...] 是手算期望；跑一次就是一次自判定。5 拍 × 5 行全对，编译器打"expect: 5/5 全等 ✅"。

第 2 集再讲这四件；这一集只看一件事——三条通路第一次同拍发出同一个数值。

三道棱面 · 逐拍对撞

三条命令、三次下降、三份产物。每一条都在同一颗 CPU（编译器）上、同一份激励上、跑同样的 5 拍：

① Python golden 直跑

bash shell 
prism run examples/adder.prism
▸ golden · Python 解释 AST
# run: adder_check design: adder_top cycle a b sum 0 1 2 3 1 10 20 30 2 100 200 300 # stop: end of stim (3 cycles) # expect: 3/3 拍有断言 · 1 列 · 全等 ✅

这一份是 golden——Python 直接解释 AST 得到的逐拍表；独立、快、可读。表尾 # expect: 3/3 ... 全等 ✅ 说的是每一行的手算期望 [3] / [30] / [300] 都命中——golden 一侧自己就能判定跑对没有。

② RTL 通路 · iverilog 真仿真

bash shell 
prism run examples/adder.prism --cosim
▸ RTL · SystemVerilog + iverilog
cycle a b sum 0 1 2 3 1 10 20 30 2 100 200 300 # stop: end of stim (3 cycles) [run --cosim] ✅ PASS: adder_check golden == RTL 仿真（3 拍 × 3 列全等） # expect: 3/3 拍有断言 · 1 列 · 全等 ✅

编译器把同一份 .prism 下降成 SystemVerilog，iverilog 真跑，输出的每一拍每一列与 golden 对齐；同一份手算期望也在 SV 侧过一遍。RTL 后端的下降 bug（位宽截断错、符号性错、握手错）会被这一步逮住。

③ TLM 通路 · SystemC 事务级

bash shell 
prism tlm examples/adder.prism
▸ TLM · SystemC + g++
Info: /OSCI/SystemC: Simulation stopped by user. cycle a b sum 0 1 2 3 1 10 20 30 2 100 200 300 [tlm] ✅ PASS: adder_check SystemC/TLM == golden（3 拍 × 3 列全等） # expect: 3/3 拍有断言 · 1 列 · 全等 ✅

编译器把同一份 .prism 下降成 SystemC/TLM C++ 源码，g++ 编译、跑 SystemC 内核，忽略调度层塌缩为事务跳转——输出的观测表仍与 golden 对齐，同一份手算期望在 TLM 侧也过一遍。这一条抓的是"时序抽象契约违反"。

三次对撞的合奏

通路 产物 仿真器 与 golden 逐拍对撞
GoldenPython AST直接解释基准
RTLSystemVerilogiverilog✅ 3×3 全等
TLMSystemC C++g++ + SystemC✅ 3×3 全等

三条通路全绿——同一份源码、三种编译产物、逐拍相同。行为等价性由编译器保证，不再需要人盯两遍代码。

"三方 cosim"抓三类 bug
  • RTL vs golden：抓 RTL 后端下降 bug——golden 走 Python AST 路径、RTL 走 SV 生成路径，两条独立。
  • TLM vs golden：抓时序抽象契约违反——TLM 忽略调度层塌缩为事务，如果塌缩逻辑错、事务粒度错，这一步会喊。
  • RTL vs TLM：两侧同源，抓的是"两份下降代码"彼此的一致性——RTL 与 TLM 之间不再是两份需要人维护等价性的产物。

神看光是好的

这就是第一集要讲完的唯一一件事——Prism 存在的理由：把两遍写、两遍盯、两遍改，合成一遍。

一颗 32 位加法器 sum = a + b——同一行代码，20 分钟前只是一段字符，现在它同时是：

  • 一段可综合 SystemVerilog，可以送进 yosys / Vivado 出 bitfile；
  • 一段 SystemC C++，可以挂进 gem5 / 事务级模型做架构探索；
  • 一张 Python 参考表，可以逐拍钉住前两条的输出。

三份产物行为等价——由编译器钉住，不再由人盯。

"神看光是好的，就把光暗分开了。神称光为昼，称暗为夜。有晚上，有早晨，这是头一日。" —— 《创世记》 1:4–5

光有了。从下一集起，我们把这份光掰开——第二集讲 Prism 的分层与语法骨架：`module` 与 `@schedule` 为什么必须分开，类型系统怎么把位宽和符号钉死，`reg` 与 `on clock` 与 `mem` 与 `fsm` 各自扮演什么角色。

第一日之后不再讲语法——因为光已经分开了。

练习

  1. 把 sum = a + b 改成 sum = a - b，跑 run --cosim——cosim 依然 PASS（golden 与 RTL 同源、同时错），但行级期望 [3] 会喊"期望 3，实得 4294967295"。这就是行级期望的意义：不给一个"从不失败"的测试留活路。
  2. 把 @schedule 里的 bitwidth : { data:32 } 删掉——Prism 会怎么报错？（提示：静态可下降性检查——信息不足时编译期报错，不静默产出劣质电路。）
  3. 把 stim 里加一行 1000, 2000, [3000],，三次下降仍全绿。
