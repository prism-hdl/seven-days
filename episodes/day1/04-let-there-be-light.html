最便宜的两道关：check 与 typecheck

工具的第一步不是生成代码，是拦住你——而且要在最便宜的地方拦。

bash解析 + 可下降性
prism check examples/mini_cpu.prism
▸ check · 轻量检查
[OK] parse succeeded modules=3 schedules=3 designs=1 [info] module 'ticker' 有 @schedule —— 可下降 RTL(CYCLE_EXACT) [info] module 'doubler' 有 @schedule —— 可下降 RTL(CYCLE_EXACT) [info] module 'thresh' 有 @schedule —— 可下降 RTL(CYCLE_EXACT)

它已经替你先回答了一个问题：三颗模块、三张 @schedule、一颗 design——全部可下降 RTL。接着把账算得更细：

bash类型 + 位宽 + 级别
prism typecheck examples/mini_cpu.prism
▸ typecheck · 位宽推导（节选）
module ticker: level : CYCLE_EXACT latency : 1 cycles can_lower_rtl: True bitwidths : cnt=7, c=7 signedness : cnt=u, c=u module doubler: bitwidths : y=8 module thresh: bitwidths : hit=1 …（每颗模块 + 每个 specialize 后的实例各一段）

cnt=7、y=8、hit=1——没有一个数字是跑出来的，全是编译期推出来的。这就是第二集说的类型驱动：位宽的账在编译器里就算清了，不留给仿真。

编译器眼里的程序

check 与 typecheck 都在验证"对不对"。换个视角：这颗设计在编译器眼里长什么样？

bashAST 树
prism dump-ast examples/mini_cpu.prism
▸ dump-ast · 节选（ticker 与 design 段）
CompilationUnit { module ticker<> @L12 { port in en: Signal<u1> port out c: Signal<u7> reg cnt: u7 on clock { cnt' = (en ? (cnt + 1) : cnt) } assign c = cnt } … design mini_cpu @L71 { inst t = ticker<> inst d = doubler<> inst h = thresh<> wire step : u8 = (t.c + 1) connect __wire__.step -> d.x expose t.cnt -> ticks } }

整棵树 82 行，源码是 103 行——同一份东西的两种记法。源码里 cnt' = en ? cnt + 1 : cnt 那行，在树里就是 on clock 节点里的一个赋值；expose t.cnt -> ticks 也没被吃掉，原样挂在 design 上。

出货：从 .prism 到可综合 SV

检查全过、树也看过了——出货。

bash生成 SystemVerilog
prism gen-rtl examples/mini_cpu.prism -o mini_cpu.sv
▸ gen-rtl · 三颗模块全部 RTL-ready
[gen-rtl] wrote mini_cpu.sv (3069 bytes) ticker@t: RTL-ready, widths={'cnt': 7, 'c': 7} doubler@d: RTL-ready, widths={'y': 8} thresh@h: RTL-ready, widths={'hit': 1}

154 行 SystemVerilog，四颗模块：ticker_rtl / doubler_rtl / thresh_rtl / mini_cpu_top。挑那颗 7 位计数器看看生成物长什么样：

systemverilogmini_cpu.sv · ticker_rtl（节选）
module ticker_rtl #(
  parameter int DW = 32
)(
  input  logic clk,
  input  logic rst_n,
  input  logic [1-1:0] en,
  output logic [7-1:0] c,
  output logic [7-1:0] xpose_cnt
);

  // 时序寄存器
  logic [7-1:0] cnt;

  // 时序更新（reset=async_low）
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      cnt <= '0;
    end else begin
      cnt <= (en ? (cnt + 1) : cnt);   // cnt' = …
    end
  end

  // 组合输出 / 局部 wire 赋值
  assign c = cnt;

  // expose 观测端口驱动
  assign xpose_cnt = cnt;

endmodule

这不是"翻译腔"的展示品——丢给 yosys，综合出 35 个门级单元：10 个 AND、11 个 XOR、7 个 D 触发器、2 个 NOT……0.77 秒。上板与整机是后面几日的事；这里只钉一件事：语言写的东西，真的能变成门。

同一份源码，三条通路

检查能拦错、树能读、SV 能出——但"跑对了吗"这三个字，谁说了算？让三台互不认识的执行者各自回答。

bashPython 参考模型

表尾那行说的是：源码 stim 里手算的期望值逐拍全中——golden 一侧自己就能判定跑对没有。

bashgolden vs 生成网表

③ TLM：SystemC 真跑

bash事务级模型
prism tlm examples/mini_cpu.prism
▸ tlm · 下降成 SystemC，编译并真跑
cycle t_en ticks step res h_hit 0 1 1 2 4 0 …（与 golden 同表，逐拍对照） [tlm] ✅ PASS: mini_cpu_check SystemC/TLM == golden（10 拍 × 5 列全等）

三条通路的共同语言只有那份 .prism：一条解释 AST，一条生成 SV 进 iverilog，一条生成 SystemC 进 g++。逐拍对撞全绿——工具的重头，就在这里。

诚实边界

本集从头到尾只有工具，没有整机、没有外设、没有上板。SoC 与 OpenSBI 是后面几日的事——这一集的任务，只是把"你将用来造它们的那套东西"一次看全。

"看全"的意思是：出错时它拦你（check / typecheck）、你想看它陪你看（dump-ast）、要出货它出货（gen-rtl）、跑没跑对它拿三台机器对（run / cosim / tlm）、连它自己缺什么、有多少保留字都记账（deps / keywords）。
