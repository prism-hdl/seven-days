这台机器跑什么

soc.prism 一共 197 行，组装六颗实例：一颗五级流水的 CPU 核、一块取指 ROM、一块数据 SRAM、以及 UART 的收发两半加一个 MMIO 寄存器面。

prismsoc.prism · design 段（节选）
design whitebow_soc {
    u_cpu  : Whitebow
    u_rom  : soc_rom
    u_dm   : sram
    u_tx   : uart_tx<CLOCK_FREQ = 1000000, BAUD_RATE = 100000>
    u_rx   : uart_rx<CLOCK_FREQ = 1000000, BAUD_RATE = 100000>
    u_regs : uart_regs

    // 取指：核 → ROM（组合读，同拍出指令）
    connect { u_cpu.im_addr -> u_rom.addr
              u_rom.rdata   -> u_cpu.im_rdata }

    // 数据口解码：字 0..2047 → dm；2048..2051 → UART 寄存器；其余读 0 不写
    wire dm_in_sram  : u1  = u_cpu.dm_addr[11] == 0
    wire uart_hit    : u1  = (u_cpu.dm_addr[11] == 1) & (u_cpu.dm_addr[10:2] == 0)
    wire dm_rdata    : u32 = dm_in_sram ? u_dm.rdata : (uart_hit ? u_regs.rd_data : 0)
    …  全文 13 根 wire / 6 颗实例
}

关键在于 u_rom 里那段真的 RISC-V 机器码——10 条指令的固件，干一件事：把收到的字节原样发回去。

prismsoc_rom 的内建固件（逐条手写机器码）
    mem ram : [2048] u32 = [
        0x000020B7,   //  0: lui  x1, 0x2       x1 = 0x2000（MMIO 基址）
        0x0080A183,   //  4: lw   x3, 8(x1)     pol: x3 = STATUS
        0x0011F193,   //  8: andi x3, x3, 1     ready?
        0xFE018CE3,   // 12: beq  x3, x0, -8    未就绪回 4
        0x0040A103,   // 16: lw   x2, 4(x1)     x2 = RXDATA（读走清 ready）
        0x0080A183,   // 20: lw   x3, 8(x1)     wai: x3 = STATUS
        0x0021F193,   // 24: andi x3, x3, 2     tx_busy?
        0xFE019CE3,   // 28: bne  x3, x0, -8    忙则回 20
        0x0020A023,   // 32: sw   x2, 0(x1)     TXDATA = x2
        0xFE1FF06F    // 36: jal  x0, -32       回 4（无限回显）
    ]

轮询 ready → 读走 RXDATA → 等 !tx_busy → 写回 TXDATA → 跳回开头。这是固件在轮询 MMIO，不是硬件直连——CPU 真的在跑一个程序。

让它跑起来

跑这台 SoC 的 run 块里有一件新东西：host 绑定。它把芯片上的两根引脚（tx_pin / rx_pin）接到真实的宿主字节流上——不是总线，是一根比特级的串口线，8N1 编码，采样率是波特率的 10 倍：

prismsoc.prism · run 段
run whitebow_soc_console of whitebow_soc {
    clock : 100 MHz
    host  : {
        console = uart_8n1(tx = u_tx.tx_pin, rx = u_rx.rx_pin, divisor = 10)
    }
    until : console.tx.count >= 3
    show  : { pcv, retire_pc, retire_rd, retire_wen,
              console.rx.count, console.rx.last, console.tx.count, console.tx.last }
}

注意 until 那一行：停机条件是"宿主已经听到 3 个字节"——不是"跑了多少拍"，不是"CPU 到哪个 PC"。程序停在哪由外部世界决定。

bash喂三个字节，听三个字节
printf 'HI\n' > /tmp/rt.rx
prism run soc.prism --host console=file:/tmp/rt
od -c /tmp/rt.tx
▸ 真实输出
cycle pcv retire_pc retire_rd retire_wen rx.count rx.last tx.count tx.last 395 12 16 2 0 3 10 2 73 397 16 4 3 1 3 10 2 73 400 8 12 25 0 3 10 2 73 405 4 8 3 1 3 10 2 73 411 4 8 3 1 3 10 2 73 417 4 8 3 1 3 10 2 73 423 4 8 3 1 3 10 3 10 # run: whitebow_soc_console 424 拍 golden 直跑完成
▸ 宿主收到的字节（od -c）

喂进去 H I \n，拿回来 H I \n——逐字节相同。这一路上发生过什么：宿主的字节 → 串口线比特流 → uart_rx 的采样状态机 → MMIO 寄存器 → CPU 轮询读走 → 写回 TXDATA → uart_tx 的发送状态机 → 串口线比特流 → 宿主。

这一集为什么值得单独写

前面三集所有的验证都是"我喂激励，我读表格"。而这一条链路上，CPU 与宿主之间没有任何共享状态——只有一根线，和两边各自对"什么是一个 8N1 帧"的理解。这已经是一台会跟外界说话的机器了。

练习

  1. 把宿主喂的字节改成别的内容（比如 printf 'abc'），until : console.tx.count >= 3 要跟着改吗？如果把 until 改成 console.tx.count >= 5 却只喂 3 个字节——判据永远等不到，想想 Prism 应该怎么办（提示：run 的判据形态是有拍数上限的——判据不可达时报错退出，而不是无限跑）。
  2. 把 divisor 从 10 改成 9——采样点偏离波特率中心。跑一次，看接收端是否还能解出字节，失败时 rx_error 会不会置起来。
  3. 用 prism gen-rtl soc.prism -o /tmp/soc.sv 自己出一份 RTL，再跑一遍上面那条 yosys 命令。对比你机器上的单元数与本集是否一致——不一致说明工具版本不同，这本身也是个值得知道的工程事实。
