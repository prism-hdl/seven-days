记忆分两层

为什么不是一种？因为取用方式不同：

短 · reg
寄存器堆
32 项，按名字取（x1、x5）。是运算的直接操作数来源，必须一拍取到。
长 · mem
字阵列
按地址取。容量大，用来放程序和数据。
更远 · SoC
片外 SRAM/DDR
第六日才出场。这里先记住：记忆是分层的，越远越慢越大。

这一集在算法层造出前两层——用的还是那个 mem 原语，但配上完全不同的读写口形状。

寄存器堆：32 个名字 + 一条铁律

prismmemory.prism · regfile
module regfile<T: bits> {
    in  raddr1 : Signal<u5>     // 读地址 1
    in  raddr2 : Signal<u5>     // 读地址 2
    in  waddr  : Signal<u5>     // 写地址
    in  wdata  : Signal<T>      // 写数据
    in  wen    : Signal<u1>     // 写使能
    out rdata1 : Signal<T>      // 读数据 1（组合）
    out rdata2 : Signal<T>      // 读数据 2（组合）

    mem regs : [32] T = 0       // 32 项阵列；复位清零

    // 组合读：x0 硬连线——读地址 0 直接给 0，不查阵列
    rdata1 = (raddr1 == 0) ? 0 : regs[raddr1]
    rdata2 = (raddr2 == 0) ? 0 : regs[raddr2]

    // 时序写：waddr == 0 丢弃
    on clock {
        regs'[waddr] = (wen & (waddr != 0)) ? wdata : regs[waddr]
    }
}

三个设计点：

  • 2 读 1 写——ALU 的两个操作数要同一拍取到，所以读口有两个、且是组合的。写口是时序的：结果在边沿落进阵列。
  • 读侧硬连线——raddr == 0 直接返回 0，根本不查阵列。这是"x0 恒零"的第一道。
  • 写侧丢弃——waddr == 0 时写不进去。这是第二道。
为什么两道都要？

RISC-V 规定 x0 恒为 0。有的人把这条规矩放在 decoder 里（"译码时发现 rd=0 就不发写使能"）。但那是把 寄存器堆自己的不变式外包给了别人——只要有任何一条路径绕过 decoder 直接驱动 waddr=0, wen=1，x0 就被写坏了。谁的状态谁负责：读口给 0、写口拒收，两道焊在 regfile 内部。等合体之后你会看到，decoder 那边还有一道门——但那是冗余的第二层，不是唯一的一层。

字阵列：为什么读必须"同拍出数"

prismmemory.prism · ram
module ram<SIZE: int> {
    in  addr  : Signal<u6>      // 字地址 0..63
    in  wdata : Signal<u32>
    out rdata : Signal<u32>
    in  wen   : Signal<u1>
    in  ren   : Signal<u1>

    mem mem : [SIZE] u32 = 0    // 字阵列，复位清零

    // 异步读：同拍出数
    rdata = ren ? mem[addr] : 0

    // 同步写
    on clock {
        if (wen) {
            mem'[addr] = wdata
        }
    }
}
如果读口是"寄存读"（下一拍才出数）会怎样？

单周期核里，pc 与数据通路共用同一个边沿：pc 指向 4 的那一拍，就得拿到地址 4 的指令。若是寄存读，你会拿到上一拍 pc 的指令——auipc / jal 算出的链接地址会差一条指令的 pc；复位后第一个边沿更糟：它会去译码存储器里的复位值 0，当成非法指令跳去异常入口。"同步读"的存储器是另一个模型，不是这颗的开关。

还有一条容易被忽略的：rdata = ren ? mem[addr] : 0。读口被 ren 门控，不读的时候给 0。不给外设发假读——第六日接上 UART 时，这条门就是"读走即消费"的开关，漏了它固件会永远等不到下一个字节。

跑起来

寄存器堆：写进去、读回来、x0 拦不拦得住

prismmemory.prism · regfile_check
design regfile_top {
    dut : regfile<T = i32>
    // 读侧的硬连线只能证明"读不出 x0"；要证明"x0 写不进"，得把阵列本身引出来看。
    expose dut.regs[0] as x0_raw
}

注意拍 4：wen=1、waddr=0、wdata=999——写请求确实发出去了，但被 regfile 拒收。rdata1 是 0（读侧硬连线），x0_raw 也是 0（写侧丢弃，阵列里根本没变）。这两列一起，才是完整证据。

哈佛：同一份源码，例化两次

RISC-V 常见两种组织：冯·诺依曼（指令与数据共用一块存储器）和哈佛（分开两块）。在 Prism 里这不是两个模块，而是同一个 ram 例化两次：

prism合体后 cpu_top 里的样子（预告）
design cpu_top {
    pc : pc<T = i32>
    im : ram<SIZE = 64>    // 指令侧
    dm : ram<SIZE = 64>    // 数据侧
    …
}

白虹的单周期核也是这个形状——只不过它是两颗各司其职的存储模块：im.prism（指令 ROM，复位时预载程序镜像、只读）与 dm.prism（泛型数据存储器，组合读 + 时序写），顶层各例化一颗。"哈佛"不是多一段控制逻辑，是多摆一颗存储、多接一根地址线。

回看：为什么第一集要讲"信息注入"

这里正是那句话的例子：ram 的算法层只有"按地址读写"，它不知道自己是 im 还是 dm——那是调度层 / 组装层的决定（例化几次、接给谁）。如果语言不允许把"做什么"和"怎么接"分开，你就得写两份几乎一样的存储器模块。

小结

  • 短记忆：寄存器堆，2 组合读 + 1 时序写；x0 由它自己保证恒零（读给 0 + 写丢弃）。
  • 长记忆：字阵列，异步读 + 同步写——单周期核必须这个形状，否则取指会晚一拍。
  • 读口要门控（ren）：不读就明确给 0，别把阵列值当"正在读"送出去。
  • 哈佛 = 同一份源码例化两次，不是两份代码。
