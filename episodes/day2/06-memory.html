记忆分两层

为什么不是一种？因为取用方式不同：

短 · reg
寄存器堆
32 项，按名字取（x1、x5）。是运算的直接操作数来源，必须一拍取到。
长 · mem
字阵列
按地址取。容量大，用来放程序和数据。
更远 · SoC
片外 SRAM/DDR
第六日才出场。这里先记住：记忆是分层的，越远越慢越大。

这一集在算法层造出前两层——用的还是那个 mem 原语，但配上完全不同的读写口形状。

寄存器堆：32 个名字 + 一条铁律

prismmemory.prism · regfile
module regfile {
    in  raddr1 : Signal<u5>     // 读地址 1
    in  raddr2 : Signal<u5>     // 读地址 2
    in  waddr  : Signal<u5>     // 写地址
    in  wdata  : Signal<i64>    // 写数据
    in  wen    : Signal<u1>     // 写使能
    out rdata1 : Signal<i64>    // 读数据 1（组合）
    out rdata2 : Signal<i64>    // 读数据 2（组合）

    mem regs : [32] i64 = 0     // 32 项 × 64 位；复位清零（上电是确定的 0，不是 x）

    // 异步读：x0 硬连线——读地址 0 直接给 0，不查阵列
    rdata1 = (raddr1 == 0) ? 0 : regs[raddr1]
    rdata2 = (raddr2 == 0) ? 0 : regs[raddr2]

    // 同步写：waddr == 0 丢弃。读侧给 0 + 写侧拒收，两道合起来才是"x0 恒零"。
    on clock {
        regs'[waddr] = (wen & (waddr != 0)) ? wdata : regs[waddr]
    }

两读一写，是三条指令数出来的

口要几个，不由设计者拍板，由指令的字段数出来：

asm四条指令的形状
        add  x3, x1, x2      # 0x002081b3  两个源操作数 + 一个目的
        sd   x3, 8(x0)       # 0x00303423  数据取 x3，基址取 x0
        jalr x1, 0(x5)       # 0x000280e7  取 x5 算目标，返回地址写 x1
        add  x0, x1, x2      # 0x00208033  目的寄存器写的是 x0——ISA 允许这条编码
  • 读口两个：add x3, x1, x2 的 rs1 与 rs2 要在同一拍都取到——ALU 的两个操作数缺一边就算不出东西。这就是两个读口的全部理由，多一个都不需要。
  • 写口一个：一条指令最多改一个寄存器（rd）。sd 那拍 rd 那格位段被借去装立即数，寄存器堆根本不写；jalr x1, 0(x5) 只写一个 x1（链接地址），它读的 x5 走的还是那两个读口。
  • 读是异步、写是同步：单周期里"取数 → 运算 → 写回"全在这一拍完成——取数不挂时钟，地址一稳就把那一格送出来；写回落在这条指令末尾的时钟边上。于是 add x1, x1, x2 连着跑几拍时，每拍读到的是上一拍落进阵列的值——存储阵列那条"同拍同址读旧值"的规则，正是在这种连续写读同一格的循环里显形的。

32 个名字里有一个不许写

第四条指令的编码是合法的：add x0, x1, x2（0x00208033）。RISC-V 规定 x0 恒为 0，但它没有禁止你把 rd 写成 0——指令照发、运算照做，只是那个结果必须当没发生。硬件里这一条由寄存器堆自己钉死：读侧 raddr == 0 直接给 0、不查阵列；写侧 waddr == 0 丢弃。

再加上"32 项 × i64"这一条：这台机器的寄存器恒为 64 位，2^32 这种数放得下也读得回（下面那张表拍 3、4 就是这一条的见证）。阵列里没有一个字节是留给"将来可能是 32 位机器"的。

为什么两道都要？

有的人把这条规矩放在 decoder 里（"译码时发现 rd=0 就不发写使能"）。但那是把 寄存器堆自己的不变式外包给了别人——只要有任何一条路径绕过 decoder 直接驱动 waddr=0, wen=1，x0 就被写坏了。谁的状态谁负责：读口给 0、写口拒收，两道焊在 regfile 内部。等合体之后你会看到，decoder 那边还有一道门（store 的 rd 位段被门成 0）——那是冗余的第二层，不是唯一的一层。

字阵列：为什么读必须"同拍出数"

prismmemory.prism · ram
module ram<SIZE: int, W: bits, A: bits> {
    // SIZE 是容量（字），A 是地址口位宽：装配面给几根地址线由总线定，这片内存
    // 有多少字由容量定，二者本就不等——64 字的片也可以挂 8 根地址线。
    in  addr  : Signal<A>       // 字地址
    in  wdata : Signal<W>       // 写数据
    out rdata : Signal<W>       // 读数据（组合，同拍出数）
    in  wen   : Signal<u1>      // 写使能
    in  ren   : Signal<u1>      // 读使能

    mem ram : [SIZE] W = 0      // 字阵列，复位清零（未初始化的阵列会读出 x）

    // 异步读：同拍出数（单周期核需要这个形状——同步读会给到上一条 pc 的数据）
    rdata = ren ? ram[addr] : 0

    // 同步写
    on clock {
        if (wen) {
            ram'[addr] = wdata
如果读口是"同步读"（挂在边沿、下一拍才出数）会怎样？

单周期核里，pc 与数据通路共用同一个边沿：pc 指向 4 的那一拍，就得拿到地址 4 的指令。若是同步读，你会拿到上一拍 pc 的指令——auipc / jal 算出的链接地址会差一条指令的 pc；复位后第一个边沿更糟：它会去译码存储器里的复位值 0，当成非法指令跳去异常入口。"同步读"的存储器是另一个模型，不是这颗的开关。

还有一条容易被忽略的：rdata = ren ? mem[addr] : 0。读口被 ren 门控，不读的时候给 0。不给外设发假读——第六日接上 UART 时，这条门就是"读走即消费"的开关，漏了它固件会永远等不到下一个字节。

哈佛：同一份源码，例化两次

RISC-V 常见两种组织：冯·诺依曼（指令与数据共用一块存储器）和哈佛（分开两块）。在 Prism 里这不是两个模块，而是同一个 ram 例化两次：

prismcpu.prism · 实例表（第九集会跑它）
design cpu_top {
    // ==== 六颗实例 ====
    pc  : pc
    rf  : regfile
    ex  : alu
    im  : ram<SIZE = 256, W = u32, A = u8>    // 指令侧：32 位字，1KB
    dm  : ram<SIZE = 256, W = i64, A = u8>    // 数据侧：64 位字，2KB
    ctl : decoder

两份宽度不是两份代码：指令恒为 32 位，数据是 64 位——RISC-V 的这条事实只落在实例参数上。白虹真核就是这个形状，它的 im 与 dm 是同一颗 SRAM 的两个实例，一个 W = u32、一个 W = u64。"哈佛"不是多一段控制逻辑，是多摆一颗存储、多接一根地址线。

回看：分层在这里兑现

第一日把"做什么"（算法层）与"怎么做、怎么接"（调度层 / 组装层）分开，这里就是那笔账的兑现处：ram 的算法层只有"按地址读写"，它不知道自己是 im 还是 dm——那是实例化时的事。如果语言不允许把这两层分开，你就得写两份几乎一模一样的存储器模块。

小结

  • 短记忆：寄存器堆，32 项 × 64 位，2 异步读 + 1 同步写；x0 由它自己保证恒零（读给 0 + 写丢弃）。
  • 长记忆：字阵列，异步读 + 同步写——单周期核必须这个形状，否则取指会晚一拍。
  • 读口要门控（ren）：不读就明确给 0，别把阵列值当"正在读"送出去。
  • 哈佛 = 同一份源码例化两次，不是两份代码。
