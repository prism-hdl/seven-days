四颗里最"干净"的一颗

decoder 是四颗器官里唯一完全不碰数据通路的：它不参与运算、不保存状态，输出只是一束控制位与几个地址。整颗模块由纯组合表达式与 match 构成——没有 reg、没有 mem、没有 fsm。

输入
instr
一条 32 位的指令字
输出 · 地址
rd / rs1 / rs2 / imm
送给寄存器堆、ALU、PC
输出 · 许可
reg_wen / mem_ren / mem_wen / is_branch…
决定这一拍允许什么发生

这个形状就是第一日讲的"理解 = 把外界字符串翻译成内部动作"。decoder 从不做事，只发号施令——做不做是别人的事。

第一步：把 32 位切开

RISC-V 的指令字是一套固定格式的位域拼图。理解的第一步就是切片：

prismdecoder.prism · 字段抽取（节选）
    // ---- 字段抽取 ----
    opcode = instr[6:0]
    funct3 = instr[14:12]
    funct7 = instr[31:25]
    funct6 = instr[31:26]     // RV64 的 shamt 有 6 位，所以移位看 funct6 而不是 funct7

    rd_raw = instr[11:7]
    rs1    = instr[19:15]
    rs2    = instr[24:20]

[hi:lo] 是位切片。注意 opcode / funct3 / funct7 都在所有指令格式里位置相同——这是 ISA 设计时刻意留的：解码器可以先看 opcode 判大类、再看 funct3/funct7 判细分，而不必先知道整条指令长什么样。

多出来的一根 funct6 是 RV64 的事：64 位机器的移位量要 6 位（0..63），指令里那一格就不够再放一个完整的 funct7 了——所以移位族用 instr[31:26] 做区分字段，剩下那一位当移量的第 6 位。同一份指令编码，宽度口径变了，字段的切法就得跟着变。

第二步：立即数的五种拼法

立即数（指令里内嵌的常量）是最麻烦的部分——五种指令格式，五种把位数重新排列的方式。RISC-V 这么做是为了让所有格式里"该固定的字段固定"。分工两步：先用一张 opcode → 形态 表判格式，再按形态把位拼回来。

prismdecoder.prism · 判格式（节选）
    // ---- 立即数：五种格式 + "无立即数"，先判格式，再按格式拼 ----
    itype = match opcode {
        0x33 => 5,     // R ：没有立即数
        0x3b => 5,     // R ：W 型同形
        0x13 => 0,     // I ：addi / lw / jalr
        0x1b => 0,     // I ：addiw / slliw …
        0x03 => 0,     // I ：load
        0x67 => 0,     // I ：jalr
        0x23 => 1,     // S ：store
        0x37 => 2,     // U ：lui
        0x17 => 2,     // U ：auipc
        0x63 => 3,     // B ：branch
        0x6f => 4,     // J ：jal
        _    => 5,     // 不认识：不给立即数
    }

拼位这件事本身没有诀窍，逐个字段搬就行。真正要选的是符号扩展怎么做——这一版把它交给类型声明：

prismdecoder.prism · 立即数（节选）
    // 符号扩展不靠减法技巧，靠【类型声明】：把位形声明成有符号线网（i12 / i13 /
    // i21 / i32），赋进 64 位端口时由类型系统扩上去。golden 按声明回绕、RTL 发
    // `logic signed`，两侧同一条规则。
    u_raw  : u32 = {instr[31:12], {12{0}}}
    i_sext : i12 = instr[31:20]
    s_sext : i12 = {instr[31:25], instr[11:7]}
    u_sext : i32 = u_raw[31:0]       // LUI/AUIPC 在 RV64 也按 bit 31 扩展（spec 2.5）
    b_sext : i13 = {instr[31:31], instr[7:7], instr[30:25], instr[11:8], 0}
    j_sext : i21 = {instr[31:31], instr[19:12], instr[20:20], instr[30:21], 0}

    imm = match itype {
        0 => i_sext,
        1 => s_sext,
        2 => u_sext,
        3 => b_sext,
        4 => j_sext,
        _ => 0,                      // R 型与未知：无立即数
    }
这一版我写错过一次——而且测试没喊

第一版 i_imm 我只写了一行：i_imm = instr >> 20。看起来和第 7 集 ALU 的逻辑右移一样干净。向量跑完 9/9 全等 ✅。

然后我加了一条负立即数（0xff800593）——立刻红：期望 -8，实得 4088。原因：instr 是无符号的 Signal<u32>，>> 是逻辑右移，不会替我们补符号位。之前那 9 条向量的立即数全是正数——正数的符号扩展和零扩展结果一样，所以测试全绿，但代码是错的。

当年的修法是每个形态都显式判"够不够半个范围再减回去"。这一版换了做法：位形声明成 i12 / i13 / i21，符号扩展由类型系统负责——白虹真核的立即数生成器也是这么写的。今天再把它改回零扩展视角试一次，那拍照样红，只是红得更早、更响：

[expect] ❌ cycle 6 imm: 期望 -8，实得 4088

而写成 i12(instr >> 20) 想强扭类型，编译器直接拦住并给出改法：类型转换 i12(x) 要求位宽相等（目标 12 位，操作数 32 位）——截断写 x[11:0]，扩位写 {k{0}} 拼接。一条老规矩仍然成立：一个测试从没失败过，说明它还没被测到。

第三步：分派

prismdecoder.prism · 分派（节选）
    // ---- opcode 分派：一次判完"这是什么指令" ----
    is_r      = (opcode == 0x33)
    is_op32   = (opcode == 0x3b)      // OP-32：addw / subw / sllw / srlw / sraw
    is_i_alu  = (opcode == 0x13)
    is_imm32  = (opcode == 0x1b)      // OP-IMM-32：addiw / slliw / srliw / sraiw
    is_load   = (opcode == 0x03)
    is_store  = (opcode == 0x23)
    is_lui    = (opcode == 0x37)
    is_auipc  = (opcode == 0x17)
    is_b      = (opcode == 0x63)
    is_j      = (opcode == 0x6f)
    is_jr     = (opcode == 0x67)

    // 算术族：ALU 选路与写回许可都来自这四条 opcode
    is_arith  = is_r | is_i_alu | is_op32 | is_imm32

    reg_wen   = is_arith | is_load | is_lui | is_auipc | is_j | is_jr
    mem_ren   = is_load
    mem_wen   = is_store
    is_branch = is_b
    is_jal    = is_j
    is_jalr   = is_jr
    is_w_op   = is_op32 | is_imm32

每条控制位都是几条布尔式的与或拼接——没有循环、没有状态、没有时序。RV64I 相比 RV32I 在这一层只多了两样东西：两个 opcode 家族（0x3b OP-32、0x1b OP-IMM-32）和一根 is_w_op。第 7 集说过，W 型指令不加长 ALU 那张表——它在这里落地成一根线。

运算选择：一张表管三族

prismdecoder.prism · ALU 选路（节选）
    // ---- ALU 运算选择：R / I / W 三族共用同一张 funct3 表 ----
    // SUB / ADD 由 funct7 分辨（只有 R 型族看它）；SRA / SRL 由 bit 30 分辨。
    // bit 30 这一位不能拿 funct7 == 0x20 代替：ADDI 的 imm[11:5] 恰好等于 0x20
    // 时（比如 addi x1, x0, 1024），整条 funct7 字段就是 0x20——那是个正数立即数，
    // 不是 SUB。
    sub_flag = (is_r | is_op32) & (funct7 == 0x20)
    sra_flag = instr[30]

    alu_op_r = match funct3 {
        0 => sub_flag ? 1 : 0,       // SUB / ADD
        1 => 5,                       // SLL
        2 => 7,                       // SLT
        3 => 9,                       // SLTU
        4 => 4,                       // XOR
        5 => sra_flag ? 6 : 8,        // SRA / SRL
        6 => 3,                       // OR
        _ => 2,                       // AND
    }

    alu_op  = is_arith ? alu_op_r : 0
    alu_src = (is_i_alu | is_imm32 | is_load | is_jr | is_store | is_lui) ? 1 : 0

同一格 funct3 的两条指令靠另一个字段区分，这件事在 64 位机器上有个新坑：funct7 == 0x20 判 SUB 只在 R 型族里成立。I 型族的 instr[31:25] 是立即数的高 7 位——addi x1, x0, 1024（0x40000093）的 funct7 字段恰好就是 0x20，照老写法它会被当成 SUB。改成先问"这是哪一族"，再看 funct7；算术右移的区分位换成 instr[30]（它在 I 型里是立即数第 10 位，在 R 型里正好是 funct7 的那一位——两种形态共用一位）。

把 sub_flag 退回老写法试一次，向量里那条 addi x1, x0, 1024 立刻红：[expect] ❌ cycle 1 alu_op: 期望 0，实得 1。

认不认识：opcode 之外还要看字段

prismdecoder.prism · 合法性（节选）
    // ---- 认不认识：opcode 之外还要看字段 ----
    // R 型族只认 funct7 = 0x00 / 0x20（0x01 是 M 扩展，这台不做）；
    // 立即数移位：shamt 占低 6 位，funct6 只许是 0x00（SLLI / SRLI）或
    // 0x10（bit 30 置起 = SRAI，仅 funct3=5）；
    // load / store 只认双字（LD/SD）；分支只认六个已定义编码。
    r_f7_ok  = funct7 in [0x00, 0x20]
    sh_ok    = (funct3 == 1) ? (funct6 == 0x00) : (funct6 in [0x00, 0x10])
    field_ok  = match opcode {
        0x33 => r_f7_ok,
        0x3b => r_f7_ok & (funct3 in [0, 1, 5]),
        0x13 => (funct3 in [0, 2, 3, 4, 6, 7]) | ((funct3 in [1, 5]) & sh_ok),
        0x1b => (funct3 == 0) | ((funct3 in [1, 5]) & sh_ok),
        0x03 => funct3 == 3,               // LD（这一颗 dm 就是 64 位字）
        0x23 => funct3 == 3,               // SD
        0x63 => funct3 in [0, 1, 4, 5, 6, 7],
        0x67 => funct3 == 0,
        0x37 => 1,
        0x17 => 1,
        0x6f => 1,
        _    => 0,
    }
    is_illegal = field_ok ? 0 : 1

"认识的 opcode"和"这条指令的字段对不对"是两件事。lb 的 opcode 是认识的，但 funct3=0 这台不做；lw（funct3=2）也一样——dm 一颗就是 64 位字，所以 load / store 只认 funct3=3，即 LD 与 SD 两条。字段对不上，同样是"不理解的字符串"。理解不了就说"我不懂"，而不是猜一个动作出来。

一个不易察觉的坑：store 的 instr[11:7] 不是 rd

S 型格式把低 5 位当 imm[4:0] 用——那一格根本不是目的寄存器。如果 decoder 不门控就把 rd_raw 报出去，store 指令会顺手把一个随机值当寄存器号送到寄存器堆。所以最后加一行：

rd = reg_wen ? rd_raw : 0

不写回时把目的寄存器报成 0——等于写 x0，天然无害。防御性默认值比"下游自己小心"可靠。

跑起来：十八拍，两个视角

十八个向量，每个都手算过期望。同一个 decoder 摆两张表——decoder_check 看"这一拍算什么"，decoder_perm 看"这一拍允许什么"。列名与上一节的 stim 表逐行对应（拍 0 是 addi x1,x0,5，往下照抄那张表的顺序）。

逐条看几处关键：

  • 拍 1：addi x1,x0,1024 的 alu_op=0——它是 ADD，不是 SUB。这一行专门盯住上面那个字段坑。
  • 拍 4、5、6、7：is_w_op=1 的四条（addw / subw / addiw / sraiw）走的还是 alu_op 里同样的 ADD / SUB / SLL / SRA。ALU 那张表没加长，多出来的是一位"结果按 32 位解释"的标记。拍 7 的 imm=1025：那是原始的 12 位字段（bit 10 是算术标志，低 6 位 1 才是移量），顶层取移位量时只走低 6 位。
  • 拍 8、9：两条访存——ld 报 mem_ren=1、sd 报 mem_wen=1，立即数是字节偏移（16 / 24）。这台只有这两条：lw 排在拍 14，已经算不认识了。
  • 拍 11、12、13：is_branch / is_jal 各自拉起；jalr 两个都不拉，它靠 alu_src=1 把基址与 imm 加出来——这三位的去处是第九集那根 pc_target 线。
  • 拍 9、11 是 store 与 branch 的 rd：两拍都报 rd=0。把 rd = reg_wen ? rd_raw : 0 那道门拿掉再跑，红的正是这两拍：cycle 9 rd: 期望 0，实得 24、cycle 11 rd: 期望 0，实得 16——S 型与 B 型都借这一格放立即数低位，那不是寄存器号。把 0 放在源头，比指望下游每一处都记得"别看它"更稳。
  • 拍 14、15、16：lw（字访问）、lb（字节访问）、mul（M 扩展）被 is_illegal 逮住。注意它们其他列照报——lw 那拍 mem_ren 仍是 1、mul 那拍 rd 仍是 5。decoder 只负责举手报告——第九集的顶层不拿这一位当门，报告先空着（处置它要等第五日的陷阱通路）。
  • 拍 17：opcode 0x7f 整族都不认识，所有许可位自然为 0。
is_illegal 只是一个位，谁来用它？

这一集的报告是完整的，处置还没装：第九集那颗 cpu_top 不拿这一位当门，非法编码照样读、照样写回，机器不停——最小机器先把真程序跑通。真核里这道门是装上的，白虹的写法是 wire rf_wen_eff : u1 = dec.reg_wen & legal -> rf.wen，一条线把"非法"翻译成"这一拍什么都不许落地"；再往上才是异常：mtvec / mcause 是第五日 CSR 那一集的活。

倒过来试一次：把 0x63 那一行的 funct3 允许集里删掉 1——bne 也会被判非法。"不认识这条指令"和"这条指令不该在此时出现"是两件事，后者才需要陷阱通路来处置。

小结

四颗器官造齐了。回头看它们各自把"水"分在了哪里：

pc
控制 → 数据
入：load / target；出：addr
regfile
地址 / 使能 vs 值
raddr / waddr / wen 是控制，rdata / wdata 是数据
alu
op vs a / b
选路信号从不参与运算
decoder
整颗都是控制
数据只在 instr 里路过
"将水分为上下。" —— 《创世记》 1:6
